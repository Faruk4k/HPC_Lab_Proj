\begin{abstract}
Hardware prefetching is an important technique for reducing the performance impact of long memory access latencies in modern processors. This project evaluates several hardware data prefetchers for scientific and memory-intensive benchmark kernels on a simulated out-of-order Armv8 architecture using gem5. The main focus is on the Access Map Pattern Matching (AMPM) prefetcher and the Indirect Memory Prefetcher (IMP), which are compared against simpler Next-line and Stride prefetchers. The evaluation considers prefetchers placed at both the L1 data cache and the shared L2 cache, using two DDR4 memory configurations. Several benchmark kernels are studied, including STREAM Triad, sparse matrix-vector multiplication, matrix multiplication, merge sort, quick sort, and breadth-first search.

The report describes the simulated architecture, benchmark selection, prefetcher configurations, and evaluation metrics. The experimental analysis focuses on speedup, prefetch accuracy, coverage, timely and late prefetches, unused prefetches, and cache miss behavior. The goal is to understand when more complex prefetchers such as AMPM and IMP provide benefits over simpler spatial prefetchers, and how prefetcher behavior changes depending on benchmark access patterns, cache placement, and memory bandwidth.
\end{abstract}

\section{Introduction}
\label{sec:intr}

Memory performance is a major bottleneck in many high-performance computing (HPC) applications. While modern processors continue to increase core counts, instruction throughput, and vector capabilities, memory latency and bandwidth often improve more slowly. As a result, applications with large working sets or irregular memory accesses may spend a significant fraction of execution time waiting for data to arrive from the memory hierarchy.

Hardware prefetching is one technique used to reduce this bottleneck. A prefetcher tries to predict future memory accesses and fetch the corresponding cache lines before they are demanded by the processor. If the prediction is correct and timely, the demand access can hit in the cache instead of stalling on a memory access. However, prefetching can also be harmful if it fetches useless cache lines, consumes memory bandwidth, or evicts useful data from the cache.

This project studies hardware prefetching for a set of scientific and memory-intensive benchmarks using the gem5 simulator. The focus is on two more advanced prefetching techniques: Access Map Pattern Matching (AMPM) and the Indirect Memory Prefetcher (IMP). AMPM is designed to identify spatial access patterns within memory regions, while IMP targets indirect memory accesses such as indexed references. These prefetchers are compared with two simpler baseline prefetchers: Next-line and Stride.

The evaluation is performed on an out-of-order Armv8 architecture model. Prefetchers are evaluated at both the L1 data cache and L2 cache, and experiments are repeated for two DDR4 memory configurations. The main goal is to analyze how different prefetchers behave across benchmarks with different memory access patterns, and to determine when complex prefetchers provide an advantage over simpler spatial prefetching mechanisms.

The rest of this report is organized as follows. Section~\ref{sec:back} introduces background on memory prefetching and the evaluated prefetchers. Section~\ref{sec:eval} describes the simulation methodology, architecture model, benchmarks, prefetcher configurations, and metrics. Section~\ref{sec:eval:res} presents the evaluation results, including speedup, cache miss behavior, prefetch accuracy, coverage, and timeliness. Finally, Section~\ref{sec:conc} summarizes the main findings and lessons learned.

\section{Background \& Related Work}
\label{sec:back}

Hardware data prefetching attempts to hide memory latency by predicting future data accesses and issuing memory requests before the corresponding load instructions require the data. A successful prefetch should be both accurate and timely: it should fetch a cache line that will actually be used, and it should arrive early enough to reduce or eliminate the demand miss latency.

Different prefetchers target different types of memory access patterns. Simple spatial prefetchers, such as Next-line, assume that future accesses are close to the current access. A Next-line prefetcher fetches the following cache line after an access, without requiring complex pattern detection. This can be effective for streaming or sequential access patterns, such as array traversal.

Stride prefetchers detect constant-distance access patterns. If a sequence of accesses follows a pattern such as consecutive cache lines or a fixed stride, the prefetcher can predict future addresses by adding the detected stride to the current address. Stride prefetching is especially relevant for scientific codes with regular array-based memory access patterns.

Access Map Pattern Matching (AMPM) is a more advanced spatial prefetcher. Instead of only tracking one stride per instruction, AMPM records access patterns within memory regions and attempts to identify multiple spatial relationships. This makes it suitable for workloads with interleaved or more complex spatial patterns. In this project, AMPM is evaluated as a representative spatial prefetcher with higher complexity than Next-line and Stride.

The Indirect Memory Prefetcher (IMP) targets indirect memory access patterns. These patterns occur when one memory access provides an index or pointer used by a later memory access. A common example is an access of the form \texttt{A[B[i]]}. Such patterns appear in sparse matrix computations, graph algorithms, and other irregular workloads. Unlike simple spatial prefetchers, IMP is intended to capture dependence-based memory behavior rather than only fixed address distances.

The evaluated benchmark set includes both regular and irregular memory access behavior. STREAM Triad and matrix multiplication contain more regular array-based accesses. Sparse matrix-vector multiplication and breadth-first search include indirect or irregular components, although their concrete implementations may still expose spatial locality through compressed or contiguous data structures. Merge sort and quick sort provide additional memory-intensive workloads with different access and control-flow behavior.

Prior work on hardware prefetching has shown that no single prefetcher is optimal for all access patterns. Aggressive prefetchers may improve performance by increasing memory-level parallelism, but they can also reduce accuracy and increase memory traffic. Therefore, this project evaluates not only speedup, but also prefetch accuracy, coverage, timeliness, unused prefetches, and cache miss behavior.

\section{Evaluation Methodology}
\label{sec:eval}

This section describes the simulation setup used to evaluate the hardware prefetchers. The evaluation uses gem5 to simulate an out-of-order Armv8 system. The experiments compare AMPM and IMP against Next-line and Stride prefetchers across several benchmark kernels, cache placements, and memory configurations.

\subsection{Architecture Model}
\label{sec:eval:arch}

The simulated system uses an out-of-order Armv8 CPU model. The core is configured with a 4-wide pipeline, a reorder buffer, physical integer and floating-point/vector registers, and a load-store queue. This setup allows memory operations to be reordered dynamically, which is important for realistic prefetcher evaluation because out-of-order execution can interleave memory streams and make access patterns more difficult to detect.

The cache hierarchy consists of private L1 instruction and data caches and a shared L2 cache. The L1 data cache and L2 cache are both evaluated as possible prefetcher insertion points. For each prefetcher family, experiments are performed with the prefetcher attached either to the L1 data cache or to the L2 cache, while the other cache level does not use that prefetcher.

Two DDR4 memory configurations are evaluated. The first configuration represents the baseline DDR4 memory setup, while the second configuration increases available memory bandwidth. These two memory configurations are used to study how prefetcher effectiveness changes when more memory bandwidth is available. This is important because aggressive prefetching can generate additional memory traffic, and its benefit may depend on whether the memory system can absorb this traffic.

\subsection{Evaluated Prefetchers}
\label{sec:eval:prefetchers}

Four prefetcher families are evaluated: Next-line, Stride, AMPM, and IMP. Next-line and Stride are used as simpler reference prefetchers. AMPM and IMP are the main focus of the project.

The Next-line prefetcher represents a simple spatial prefetching strategy. It assumes that future memory accesses are likely to continue to the next cache line. This prefetcher has low complexity and can be effective for streaming memory accesses.

The Stride prefetcher detects regular address differences between memory accesses. Once a stable stride is detected, it issues prefetch requests for future addresses following the same stride. This prefetcher is expected to perform well for regular array-based access patterns.

AMPM tracks accesses within memory regions and attempts to identify spatial patterns from the observed access map. Compared with Next-line and Stride, AMPM can potentially detect more complex spatial patterns and multiple interleaved streams.

IMP targets indirect memory access patterns, where one loaded value is used to compute the address of a later memory access. This makes IMP relevant for sparse and graph-based workloads, where indexed memory references are common.

For each prefetcher, both default and tuned configurations are considered where applicable. The tuned configurations vary relevant prefetcher parameters such as prefetch degree, distance, thresholds, table sizes, and other prefetcher-specific parameters. The final comparison reports both default behavior and the best-performing tuned configuration.

\subsection{Experimental Design}
\label{sec:eval:design}

Each benchmark is simulated under multiple prefetcher configurations. The experiments vary the prefetcher family, prefetcher configuration, cache placement, and memory configuration. A no-prefetch baseline is also simulated for each benchmark and memory configuration.

The primary comparison is speedup relative to the no-prefetch baseline. For each benchmark and system configuration, the best-performing configuration of each prefetcher family is selected. In addition, the default configuration of each prefetcher family is recorded and shown as a reference. This allows the analysis to distinguish between the default behavior of a prefetcher and the improvement obtained through parameter tuning.

    \item Prefetcher families: Next-line, Stride, AMPM, IMP.
    \item Cache placement: L1 data cache and L2 cache.
    \item Memory configurations: DDR4 1x and DDR4 2x.
    \item Baseline: no hardware data prefetching.
    \item Evaluation modes: default prefetcher configuration and tuned configurations.

\subsection{Metrics}
\label{sec:eval:metric}

Several metrics are used to evaluate prefetcher behavior. Speedup measures the overall performance improvement relative to the no-prefetch baseline. Cache miss rates are used to determine whether a prefetcher reduces demand misses. Prefetch accuracy and coverage are used to evaluate how effectively the prefetcher predicts useful memory accesses. Timely, late, and unused prefetches are used to distinguish between useful prefetches that arrive early enough, useful prefetches that arrive too late, and prefetches that are never used.

\begin{table}[h]
\caption{Evaluation metrics.}
\centering
\begin{tabular}{|l|l|}
\hline
Metric & Description \\ \hline
Simulation time & Runtime reported by gem5 for the benchmark region \\ \hline
Speedup & No-prefetch simulation time divided by prefetcher simulation time \\ \hline
IPC & Instructions per cycle, used to observe core-level performance changes \\ \hline
Demand misses & Cache misses caused by demand accesses \\ \hline
Miss rate & Demand misses divided by demand accesses \\ \hline
Prefetches issued & Number of prefetch requests generated by the prefetcher \\ \hline
Useful prefetches & Prefetched cache lines that are later used by demand accesses \\ \hline
Unused prefetches & Prefetched cache lines that are not used before eviction \\ \hline
Prefetch accuracy & Fraction of issued prefetches that are useful \\ \hline
Prefetch coverage & Fraction of potential demand misses covered by useful prefetches \\ \hline
Timely prefetches & Useful prefetches that arrive before the demand access \\ \hline
Late prefetches & Useful prefetches that arrive too late to fully hide latency \\ \hline
\end{tabular}
\label{tab:metrics}
\end{table}

The main speedup metric is calculated relative to the no-prefetch baseline:

\begin{equation}
\text{Speedup} =
\frac{T_{\text{no-prefetch}}}{T_{\text{prefetcher}}}
\end{equation}

where $T_{\text{no-prefetch}}$ is the simulation time without hardware prefetching and $T_{\text{prefetcher}}$ is the simulation time with a given prefetcher configuration.

Prefetch accuracy is calculated as:

\begin{equation}
\text{Accuracy} =
\frac{\text{Useful prefetches}}{\text{Issued prefetches}}
\end{equation}

Prefetch coverage is calculated as:

\begin{equation}
\text{Coverage} =
\frac{\text{Useful prefetches}}
{\text{Useful prefetches} + \text{Demand misses}}
\end{equation}

These metrics are analyzed together because high speedup does not necessarily imply high accuracy. A prefetcher may improve performance despite lower accuracy if it generates enough timely prefetches and the memory system has sufficient bandwidth. Conversely, a prefetcher may have high accuracy but low speedup if its prefetches arrive too late or if it does not issue enough requests.

\subsection{Effect of Cache Placement}
\label{sec:res:cache-placement}

This subsection compares prefetching at the L1 data cache with prefetching at the L2 cache. Prefetching at L1D can potentially reduce latency earlier in the hierarchy, but it may also increase pressure on the small L1 cache. Prefetching at L2 has more cache capacity available and may avoid some L1 pollution, but it may be less effective if prefetches arrive too late for the core.

The analysis should compare the same benchmark and prefetcher family across L1D and L2 placement. Important questions include:

\begin{itemize}
    \item Does a prefetcher perform better at L1D or L2?
    \item Does the preferred placement depend on benchmark access pattern?
    \item Does L2 placement reduce harmful cache pollution?
    \item Does L1D placement improve timeliness?
\end{itemize}

\subsection{Effect of Memory Bandwidth}
\label{sec:res:memory}

This subsection compares DDR4 1x and DDR4 2x memory configurations. Prefetching can increase memory-level parallelism and hide latency, but aggressive prefetching can also generate additional traffic. Therefore, the effectiveness of a prefetcher may depend on available memory bandwidth.

The analysis should identify whether increasing memory bandwidth improves the benefit of aggressive prefetching. This is particularly relevant for memory-intensive benchmarks such as STREAM Triad and SpMV. If a benchmark is bandwidth-limited, higher bandwidth may allow more prefetch requests to be useful. If the memory system is already saturated, additional prefetch traffic may provide limited benefit.

\subsection{Prefetch Accuracy and Coverage}
\label{sec:res:accuracy-coverage}

Prefetch accuracy and coverage explain how well a prefetcher predicts useful cache lines. Accuracy measures the fraction of issued prefetches that are later used. Coverage measures how much of the demand-miss stream is covered by useful prefetches.

A high-accuracy prefetcher is conservative and avoids useless prefetches, but may not issue enough requests to cover many misses. A lower-accuracy prefetcher may still improve performance if it provides high coverage and enough timely prefetches. Therefore, accuracy and coverage must be analyzed together.

\subsection{Timely, Late, and Unused Prefetches}
\label{sec:res:timely-late-unused}

A useful prefetch improves performance only if it arrives early enough. Therefore, prefetches are separated into timely, late, and unused categories. Timely prefetches arrive before the demand access and can hide latency. Late prefetches are useful but arrive too late to fully hide latency. Unused prefetches consume bandwidth and cache capacity without helping performance.

\subsubsection{STREAM Triad}
STREAM Triad is expected to favor simple spatial prefetchers because it contains regular streaming memory accesses. The analysis should compare whether Next-line and Stride outperform AMPM and IMP, and whether higher memory bandwidth improves the benefit of aggressive prefetching.

\subsubsection{SpMV}
SpMV contains sparse and indirect memory behavior, making it an important benchmark for IMP. The analysis should determine whether IMP provides an advantage over spatial prefetchers, and whether AMPM can exploit spatial structure in the sparse matrix representation. Coverage and timeliness are especially important for this benchmark.

\subsubsection{Matrix Multiplication}
Matrix multiplication has regular array-based behavior but may also have cache reuse depending on the implementation and problem size. The analysis should explain whether prefetchers provide only modest improvement or whether specific configurations reduce cache misses significantly.

\subsubsection{Merge Sort}
Merge sort has data movement and comparison behavior that may expose sequential accesses during merging. The analysis should determine whether spatial prefetchers are sufficient or whether AMPM/IMP provide additional benefit.

\subsubsection{Quick Sort}
Quick sort has data-dependent partitioning behavior. The analysis should examine whether prefetchers improve performance consistently or whether irregular control flow limits prefetch effectiveness.

\subsubsection{BFS}
BFS is algorithmically irregular, but the implementation uses an adjacency-array representation. Therefore, the edge traversal contains sequential scans through the edge array, while accesses to the visited array are indirect. The analysis should explain whether the observed performance is dominated by the sequential edge traversal or by the indirect visited-array accesses. This is important for understanding why IMP may or may not outperform Next-line and Stride.

\section{Conclusion}
\label{sec:conc}

This project evaluated hardware data prefetching for a set of scientific and memory-intensive benchmarks on a simulated out-of-order Armv8 architecture. The main focus was on AMPM and IMP, which were compared against simpler Next-line and Stride prefetchers. The evaluation considered both L1D and L2 prefetcher placement, two DDR4 memory configurations, and both default and tuned prefetcher configurations.

The results show that prefetcher effectiveness depends strongly on benchmark memory access patterns. Simple spatial prefetchers can be highly effective for workloads with regular or streaming behavior. More complex prefetchers such as AMPM and IMP are expected to provide benefits when the benchmark exposes the type of access pattern they are designed for, such as multiple spatial streams or indirect memory references.

A key lesson is that algorithmic irregularity does not always imply that an indirect prefetcher will dominate. For example, a BFS implementation using contiguous adjacency arrays may still expose strong spatial locality during edge traversal, allowing Next-line or Stride prefetchers to perform well. Similarly, sparse workloads may contain both indirect accesses and regular streams, so the best prefetcher depends on which part of the memory behavior dominates execution time.

The evaluation also highlights the importance of analyzing more than speedup alone. Cache miss rates, prefetch accuracy, coverage, timely prefetches, late prefetches, and unused prefetches are necessary to explain why a prefetcher improves or fails to improve performance. A prefetcher with lower accuracy may still perform well if it produces many timely prefetches and the memory system has sufficient bandwidth. Conversely, a prefetcher with high accuracy may provide limited speedup if its prefetches arrive too late or cover too few misses.

The final report will complete this analysis by adding the AMPM results, the final Stage 3 IMP results, and detailed plots for speedup, default-versus-tuned behavior, cache miss rates, prefetch coverage, accuracy, timeliness, and unused prefetches.
